Problem

if문으로 질문을 하나씩 처리하면 금방 한계가 옵니다

사용자 표현은 계속 달라집니다

같은 의미라도 질문 방식이 제각각입니다.

내일 바람 약한 곳? 낼 어디가 잔잔해? 오후 풍속 낮은 지점 바람 제일 안 부는 지역

문장별로 대응하면 표현이 하나 늘 때마다 규칙을 추가해야 합니다.

잘못된 접근

if "내일" in question:
    ...
elif "바람" in question:
    ...
elif "약한" in question:
    ...

질문 표현이 늘어날수록 유지보수가 어려워지고 누락이 많아집니다.

문장별 처리 → 의도별 처리로 전환3
Why not endless if statements?

모든 문장을 if문으로 만드는 것은
모든 주문을 통째로 외우는 것과 같습니다

같은 볶음밥 주문도 표현은 계속 달라집니다

볶음밥 주세요 볶음밥 하나 부탁해요 밥 볶은 음식 먹고 싶어요 볶음밥 한 그릇 가능할까요? 
if 질문 == "볶음밥 주세요":
    볶음밥을_만든다()
elif 질문 == "볶음밥 하나 부탁해요":
    볶음밥을_만든다()
# 새로운 표현이 생길 때마다 계속 추가

해양예보 질문은 조건까지 서로 조합됩니다

날짜 4개
오늘·내일·모레·주말

시간 3개
오전·오후·종일

어종 7개
참돔·우럭·농어 등

지표 6개
파고·기온·수온 등

4 × 3 × 7 × 6 × 계산 4가지
= 2,016가지 조합

여기에 사람마다 다른 말투까지 더해지므로, 문장별 if문은 빠르게 감당하기 어려워집니다.

if문 방식 = 가능한 모든 문장을 하나씩 외우는 방식4

주방은 몇 가지 조리법만 준비합니다

목록, 상세, 순위, 조건, 개수, 비교, 추세, 추천 등 약 10개의 범용 기능을 질문 조건에 맞게 조합합니다.

새로운 말투가 들어와도 같은 JSON 주문서로 바뀌면 Python 함수를 새로 만들 필요가 없습니다.

메뉴에 없는 주문은 마음대로 만들지 않습니다

CSV에 없거나 지원하지 않는 질문은 실행 전에 검사하고, 가능한 범위를 다시 안내합니다.

예: “근처 맛집도 알려줘” → “현재 지수 파일에는 맛집 정보가 없습니다. 해양예보 정보는 안내할 수 있습니다.”

LLM은 통역, JSON은 표준 주문서, Python은 검증된 계산5
How LLM understands language

LLM은 많은 문장에서
“다른 말, 같은 뜻”의 패턴을 배웁니다

아이도 여러 표현을 경험하며 뜻을 연결합니다

물을 주세요 물 좀 줄래? 목말라 마실 것 있어?

문장은 달라도 비슷한 상황에서 반복되면, 모두 “물을 원한다”는 뜻과 연결됩니다.

표현을 숫자 좌표로 바꾸고 서로의 관계를 학습합니다

제일 높다 ≈ 가장 높다 ≈ 최고다
파도가 낮다 ≈ 물결이 잔잔하다
어디가 좋아? ≈ 적합한 지역 추천

문맥도 함께 확인 “기온이 높다”는 평균기온, “파도가 높다”는 평균파고, “점수가 높다”는 총점수를 선택합니다.

처음 보는 말투도 학습한 의미 관계를 이용해 일반화6
Meaning as numbers

“숫자 패턴”은 말의 뜻을
숫자로 된 의미지도에 놓는 것입니다

지도에서 가까우면 쓰임도 비슷합니다

“제일 따뜻한 곳”
[ 0.82, -0.14, 0.67, … ]
“기온이 가장 높은 지역”
[ 0.80, -0.11, 0.70, … ]

숫자는 이해를 돕기 위한 예시입니다. 실제 모델은 수백~수천 개 숫자로 된 좌표를 사용하며, 각 숫자 하나에 고정된 뜻이 있는 것은 아닙니다.

많은 문장을 읽으며 지도를 조금씩 고칩니다

1

문장을 작은 단위로 나눕니다.

2

각 단위를 숫자 좌표로 바꿉니다.

3

다음에 올 말을 맞혀봅니다.

4

틀린 만큼 내부 숫자를 조정합니다.

이 과정을 아주 많이 반복하면 “잔잔한 바다”와 “파도가 낮은 곳”처럼 비슷한 상황에서 쓰이는 표현이 가까운 관계로 자리 잡습니다.

쉽게 말하면 LLM은 단어 뜻을 사전처럼 한 줄로 외우기보다, 어떤 말이 어떤 말과 자주 어울리는지를 거대한 숫자 지도에 기록합니다.

문장 → 숫자 좌표(벡터) → 관계 학습 → 비슷한 표현 이해7
Training vs service

자동으로 고치는 것은 “학습할 때”이고,
서비스 중에는 모델의 숫자가 고정됩니다

학습 단계

문제를 풀고 자동 채점하며 조금씩 수정

문제: "파도가 낮아서 바다가 ___"

모델 예측: "뜨겁다"  ✕
실제 문장: "잔잔하다" ○

→ 틀린 정도를 계산
→ 내부 숫자를 아주 조금 조정

개발자가 학습 방법과 데이터를 준비하면, 학습 프로그램이 오차를 계산해 모델의 내부 숫자(가중치)를 자동으로 조정합니다.

서비스 단계

다운로드한 모델은 대화만으로 변하지 않음

학습이 끝난 Qwen3-8B
→
우리 서버에 다운로드
내부 숫자 고정
→
질문을 많이 받아도
저절로 재학습하지 않음

서비스 개선 방법 잘못 이해한 질문을 모아 프롬프트와 JSON 예시를 보완하거나, 필요할 때 별도의 미세조정을 수행합니다.

자동 학습과 실시간 대화는 서로 다른 단계8
Guide & guardrails

언어 능력에 우리 서비스의 규칙과 예시를 더합니다

허용할 필드와 변환 규칙을 알려줍니다

사용 가능 지표:
평균파고, 평균수온, 평균기온,
평균풍속, 평균유속, 총점수, 예보지수

"가장 높다" → sort: "desc"
"가장 낮다" → sort: "asc"
"전부"       → return_all: true

실제 질문과 정답 JSON 예시를 함께 주면, 새로운 말투도 같은 형식으로 변환하기 쉬워집니다.

LLM도 애매한 말은 틀릴 수 있습니다

“물이 좋은 곳 알려줘”

수온이 적절한 곳? 파도가 낮은 곳? 총점이 높은 곳?

뜻이 하나로 정해지지 않으면 추측하지 않고 사용자에게 기준을 다시 묻습니다.

안전장치 CSV에 있는 필드만 허용하고, Python이 JSON을 검사한 뒤 실행하며, 없는 정보는 답변하지 않습니다.

LLM의 일반화 능력 + 서비스 규칙 + Python 검증9

중요 판단 근거와 수치는 기존 지수 산출 결과와 DB에서 가져오고, LLM은 표현과 질문 이해를 담당합니다.

이렇게 나누면 챗봇 답변과 기존 웹 표출 지수가 서로 다르게 나오는 위험을 줄일 수 있습니다.

Source of Truth = CSV/DB10
Example

예시: “내일 오후 바람 가장 약한 지역 알려줘”

LLM이 추출할 JSON

{
  "date": "내일",
  "time": "PM",
  "region": "ALL",
  "variable": "평균풍속",
  "operation": "min",
  "intent": "ranking"
}

Python/DB가 수행할 작업

target = df[
  (df["예측일자"] == target_date) &
  (df["시간"] == "PM")
]

result = target.sort_values("평균풍속").head(5)

최종 답변 방향

“내일 오후 기준 평균풍속이 가장 낮은 지역은 ○○이며, 평균풍속은 ○○m/s입니다. 다음으로 ○○, ○○ 순입니다.”

복잡한 표현도 같은 JSON 구조로 정규화11

데이터는 매일 갱신

모델 학습 ≠ 서비스 구축. 대부분은 연결·검증·운영 설계입니다.12

오프라인 구축의 장점

  • 외부 API 호출 없이 내부 서버에서 처리
  • 질문당 API 토큰 비용 없음
  • 민감한 예보 데이터와 로그를 내부망에 보관
  • 모델은 고정하고 예보 데이터만 매일 갱신 가능

대신 GPU, RAM, 동시 사용자 수, 모델 크기에 따라 응답속도가 달라집니다.

Performance

동시 사용자가 늘면 느려질 수 있습니다

1

주 병목

CSV/DB 조회보다 로컬 LLM 추론이 가장 무겁습니다.

2

해결 방향

Queue, 캐시, 타임아웃, 동시 요청 제한으로 서버 다운을 방지합니다.

3

설계 원칙

LLM에는 계산을 시키지 말고 조건 추출과 설명만 맡깁니다.

총 이용자 수보다 중요한 것은 동시 질문 수입니다.

대국민 서비스라도 실제 동시 사용자가 많지 않다면, 4B~8B급 모델부터 검증하는 것이 현실적입니다.

성능은 서버 사양·모델 크기·동시 요청 수로 결정14

AI 기업·연구팀

공개되는 것

모델 가중치

학습이 끝난 모델 파일을 공개하면, 기관 서버에 다운로드해 로컬로 실행할 수 있습니다.

연결·검증·운영
